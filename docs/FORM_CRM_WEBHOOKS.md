# Инструкция: заявки сайта, вебхуки и Битрикс24

Актуальность: 19.11.2026. Проверено по коду и действующим связям форм на latitudo.ru.
Документ описывает существующую реализацию, а не стандартную интеграцию Битрикса.

## 2. Где менять ответственного

### У одного уже созданного лида

1. В админке сайта: **Сервисы → Веб-формы → Результаты → нужная форма**.
2. В колонке «Отправлено в CRM» нажать «Лид #…».
3. В карточке Битрикс24 открыть «Общие», найти «Ответственный», нажать «Сменить».
4. Выбрать сотрудника, сохранить карточку, проверить результат.
5. Если ответственный снова изменился, открыть вкладку «История»: посмотреть запись о смене и автора.

Это меняет выбранный лид, но не правило назначения будущих заявок.

### Начальный ответственный для всех новых заявок семи форм

Сейчас в `local/php_interface/include/latitudo_form_crm_delivery.php`, метод `send()`:

```php
$fields['ASSIGNED_BY_ID'] = 65;
```

65 — Дмитрий Ошкин. Значение общее для всех семи форм. Его **нет в настройке вебхука или в отдельном поле админки сайта**.
Изменение владельца вебхука тоже не заменяет эту настройку: создатель/автор REST-запроса и ответственный за лид — разные роли.

Порядок изменения для разработчика:

1. Уточнить нужного сотрудника и его числовой ID в Битрикс24 (в URL профиля обычно `/company/personal/user/ID/`).
2. Проверить, что сотрудник активен и работает с лидами. Не подставлять ID пользователя админки сайта: это другая база пользователей.
3. Изменить `ASSIGNED_BY_ID` в указанном методе. Связи полей формы не подходят для этого: код перезаписывает `ASSIGNED_BY_ID` перед отправкой.
4. Обновить информационную надпись в `latitudo_form_crm.php` → `adminFormNote()`, проверки ожидаемого ID в тестах, текст CLI-миграции и документацию.
5. Выполнить `test_delivery.php`, `test_bitrix.php`, PHP lint. Проверить фактический серверный код, подготовить резервную копию.
6. После отдельного разрешения на прод выложить только затронутые файлы.
7. Выполнить согласованную контрольную заявку. Проверить начальное назначение в истории и конечного ответственного после выполнения правил CRM.

Правка затронет ещё не отправленные заявки при их следующей отправке. Уже созданные лиды не переназначаются.
Разные начальные ответственные для разных форм сейчас не настроены: для этого требуется отдельная доработка конфигурации по ID формы.

### Кому лид достаётся после распределения внутри CRM

Сайт передаёт 65, но CRM может затем поменять ответственного. Это уже произошло в контрольных заявках:
в [истории лида 217893](https://latitudo.bitrix24.ru/crm/lead/details/217893/) зафиксировано
**«Дмитрий Ошкин → РОП Москва»**, автор изменения — «Админ Латитудо».
ID «РОП Москва» — 2475. В карточке есть информация об автоматическом распределении в отдел МОСКВА.

Чтобы изменить постоянное распределение, нужно менять правило внутри Битрикс24:

1. Открыть пример лида и вкладку «История»: определить, когда и кем меняется ответственный.
2. Проверить автоматизацию лидов: роботы на стадии «Поступил новый лид» и бизнес-процессы, запускаемые при создании/изменении.
3. Найти действие изменения ответственного и условия распределения (в частности, домен/регион/источник).
4. Согласовать новое правило и список затронутых заявок. Сохранить копию/экспорт изменяемой настройки.
5. Изменить нужное действие, затем проверить подходящую под его условия тестовую заявку и историю назначений.

**Конкретный шаблон/ID робота или бизнес-процесса пока не установлен.** Название автора в истории само по себе не указывает точный шаблон.
Не следует отключать всю автоматизацию или принудительно переназначать лид после каждого её запуска.
Если требуется, чтобы всегда оставался Дмитрий, одной строки `ASSIGNED_BY_ID=65` недостаточно: нужно согласовать исключение в распределении CRM.

## 3. Как проходит заявка

1. Штатный механизм веб-форм сохраняет результат в базе сайта.
2. Событие `onAfterResultAdd` помещает ID результата в `b_latitudo_form_crm` со статусом `pending`.
3. Почтовое уведомление отправляется существующим механизмом формы, независимо от REST. Получатели/шаблоны переносом не менялись.
4. Агент `LatitudoFormCrm::runQueue();` читает очередь и отправляет до трёх заявок за запуск.
5. Перед созданием выполняется `crm.lead.list` по точным идентификаторам результата. Если лид уже есть, используется его ID.
6. Если лида нет и исход предыдущей попытки известен, вызывается `crm.lead.add`.
7. После получения ID сайт сохраняет его в очереди, выставляет штатный `SENT_TO_CRM=Y`; в результатах появляется ссылка.
8. Далее CRM выполняет собственные правила: распределение, задачи, изменение источника, контроль дублей и т. п.

Интервал агента — 60 секунд. На сервере cron запускает `/bitrix/php_interface/cron_events.php` каждую минуту.
Фактическая задержка зависит от расписания, очереди и времени ответа CRM; мгновенное появление лида не гарантируется.
При недоступности CRM сохранённый результат и почтовая отправка не зависят от её ответа.

Общий вебхук портала `latitudo.bitrix24.ru` хранится на сервере вне публичного каталога:
`/var/www/u0916578/data/.latitudo_b24.php`, ключ массива `webhook`.
Токен/полный URL не публиковать, не записывать в Git, инструкции, скриншоты или сообщения.
Новый транспорт проверяет HTTPS, сертификат и точный хост; таймаут соединения 5 секунд, ответа 20 секунд.

## 4. Где смотреть и что означают статусы

Открыть [список форм](https://latitudo.ru/bitrix/admin/form_list.php?lang=ru), выбрать результаты нужной формы.
Например, [результаты общей формы](https://latitudo.ru/bitrix/admin/form_result_list.php?lang=ru&WEB_FORM_ID=19).
Колонка «Отправлено в CRM» показывает:

| Статус | Значение и действие |
|---|---|
| Ожидает отправки | Заявка в очереди. Обновить список после запуска агента. |
| Отправляется | Попытка началась, результат ещё не зафиксирован. |
| Отправлено + Лид #… | CRM подтвердила ID. Ссылка ведёт в карточку. |
| Ошибка отправки | Есть явная ошибка или не удалась предварительная проверка. Прочитать текст, исправить причину; затем выполнить ручную отправку. Автоповтора состояния `error` нет. |
| Результат отправки уточняется | Ответ потерян/неоднозначен. Система ищет уже созданный лид и не создаёт второй вслепую. Требуется проверка при длительном ожидании. |
| Только старый зелёный значок | Исторический результат со штатным флагом, но без ID в новой очереди. Новая ссылка автоматически не восстанавливается. |

Штатный фильтр «Отправлено в CRM» использует `SENT_TO_CRM`: «Да» — подтверждённая отправка,
«Нет» — также ожидание/ошибка/неопределённый исход. Это не отдельный фильтр по каждому состоянию очереди.
Статус CRM не подтверждает получение письма адресатом, доставку вложения отдельным агентом калькулятора или конечного ответственного.

Для ручной попытки использовать действие «Отправить в CRM» у нужного результата, имея права на форму/результат.
Для этих семи форм оно перехватывается новым REST-обработчиком; сессия и права проверяются.
Если ID уже сохранён, повтор не создаёт второй лид. Статус/ссылку после действия проверить обновлением списка.
Ранее отправленный старой интеграцией результат (`SENT_TO_CRM=Y` без нового ID) повторно не создаётся.
Ручная отправка исторического неотправленного результата может создать новый лид: сначала проверить необходимость и наличие старого лида в CRM.

## 5. Какие данные передаются

Передаются связанные поля из вкладки CRM конкретной формы, плюс служебные поля ниже.
Не все вопросы формы автоматически отправляются в CRM. Полная таблица каждой формы приведена в приложении.

| Служебное поле REST | Значение |
|---|---|
| ASSIGNED_BY_ID | 65; устанавливается кодом перед созданием |
| SOURCE_ID | WEB по текущему преобразователю; CRM может преобразовать источник своими правилами |
| ORIGINATOR_ID | latitudo.ru:webform |
| ORIGIN_ID | `<ID формы>:<ID результата>`, например `19:15208` |
| params.REGISTER_SONET_EVENT | Y; параметр вызова, не поле лида |

`PHONE_WORK` из старой связи превращается в `PHONE: [{VALUE: "…", VALUE_TYPE: "WORK"}]`.
`EMAIL_WORK` — аналогично в `EMAIL`. Несколько обычных значений объединяются через запятую.
Если значение отсутствует, обычное связанное поле может передаваться пустой строкой;
для телефона/email без значений элемент не создаётся. Пустой заголовок TITLE останавливает создание с ошибкой.
Код не дополняет отсутствующий город/UTM и не отправляет автоматически каждый скрытый вопрос формы.

Особенности:

- TOORDER: название товара → COMMENTS, сообщение клиента → UF_CRM_1670914076118. ID товара не имеет отдельной связи CRM в текущей конфигурации.
- MAINFORM: TITLE берётся из NAMEFORM (подпись кнопки/сценария), вопрос → COMMENTS, вариант связи → UF_CRM_1670914321940.
- CLAIM: TITLE из NAMEFORM, файл → UF_CRM_1772713891. Отдельного COMMENTS в действующих связях нет.
- Общая строка UTM передаётся только у MAINFORM и WHATSAPP. Отдельные UTM_SOURCE/MEDIUM/CAMPAIGN/CONTENT/TERM/GEO передаются у всех семи форм.
- WhatsApp/Telegram/MAX отправляют введённый номер как рабочий PHONE, а не как IM-идентификатор чата.

Файл CLAIM: читается сохранённый файл сайта и передаётся в множественное поле
`UF_CRM_1772713891: [{fileData: [имя_файла, base64_содержимое]}]` при создании лида.
Если файл заявки недоступен, обработчик сообщает ошибку, а не подтверждает отправку без файла.
Прежний обработчик продолжает вкладывать файл в письмо, но не создаёт повторную CRM-загрузку для REST-заявки.

PDF калькулятора — дополнительный сценарий MAINFORM «Рассчитать с менеджером»:
PDF вкладывается в письмо; отдельный агент добавляет комментарий со сметой и PDF в ленту,
PDF в UF_CRM_1772713891, а пустую сумму лида заполняет итогом расчёта (OPPORTUNITY, CURRENCY_ID=RUB).
Для REST-заявки агент использует сохранённый lead_id. Это отдельная операция после создания лида;
индикатор «Отправлено» сам по себе не подтверждает выполнение этого агента.

## 6. Как менять связи полей

1. Админка сайта → Сервисы → Веб-формы → Настройка форм → нужная форма → CRM.
2. Проверить выбранное подключение и блок «Связанные поля»: слева поле CRM, справа вопрос формы.
3. До изменения зафиксировать текущие связи; для изменения рабочей базы сохранить проверенную резервную копию вне www.
4. Убедиться, что целевое поле существует в CRM, доступно для записи и его тип поддержан преобразователем.
5. Изменить нужную связь и сохранить. Не удалять существующие связи без причины.
6. Контрольная заявка должна подтвердить реальное значение в карточке CRM.
7. Разработчик обновляет проверенный снимок `tools/form-crm/mappings.json` и эту инструкцию.

Источник связей при обычной отправке — база сайта (`b_form_crm_link`, `b_form_crm_field`), а не mappings.json.
JSON — контрольный снимок для миграции: после изменения связей check/enable/disable откажутся работать,
пока изменения не проверены и снимок не обновлён. Нельзя просто снимать эту проверку.
Текущая поддержка файлов специальная — UF_CRM_1772713891. Добавление другого файлового поля,
списков со сложными ID или новой формы требует проверки/доработки преобразователя.

Режим старого подключения должен оставаться **«вручную»**. Автоматическую отправку выполняет новая очередь.
Обработчик сохраняет M для включённых форм при сохранении настроек. Не пытаться включить второй автоматический канал:
это может привести к дублям. Проверка соединения старого URL `/crm/configs/import/lead.php`
не проверяет новый REST-вебхук; прежняя ошибка OTP required относится к старой авторизации.

## 7. Почта

Настройки уведомлений независимы от REST. Управление шаблонами:
**Настройки → Настройки продукта → Почтовые события → Почтовые шаблоны** (названия меню могут зависеть от версии).
Найти тип `FORM_FILLING_<SID>` и активный шаблон, проверить «Кому», копии и подстановки.
Для корзины тип — `NEW_ONE_CLICK_BUY`.

По проверке при переносе: MAINFORM/TOORDER/CLAIM → formsort@latitudo.ru;
WHATSAPP/PROPUSK/TELEGRAM/MAX → formsort1@latitudo.ru; корзина → korzina@latitudo.ru;
RESUME → hr@latitudo.ru и content@latitudo.ru; REVIEW — адрес по умолчанию из почтовой настройки/шаблона.
Перед изменением получателей заново сверять фактический активный шаблон: документация не подменяет его настройки.

Значение `SUCCESS_EXEC=Y` у события `b_event` означает успешную обработку отправки на стороне сайта,
но не доказывает попадание во входящие (проверять также спам/отказы/почтовый ящик).
Почта не должна использоваться как второй импорт того же обращения в CRM без согласованной защиты от дублей.

## 8. Диагностика и обслуживание для разработчика

Файлы реализации:

| Файл | Назначение |
|---|---|
| local/init.php | Подключает обработчик |
| local/php_interface/include/latitudo_form_crm.php | События, очередь, транспорт, права, интерфейс, загрузка файлов |
| local/php_interface/include/latitudo_form_crm_delivery.php | Преобразование полей, начальный ответственный, защита от повторного создания |
| local/php_interface/include/latitudo_terrace_calc_crm.php | PDF и комментарий калькулятора |
| bitrix/php_interface/include/claim_file_crm.php | Вложение претензии в письмо, совместимость со старым агентом |
| tools/form-crm/overrides/claim_file_crm.php | Версия последнего файла в Git для выкладки |
| tools/form-crm/migrate.php | Проверка/включение/отключение по ID формы |
| tools/form-crm/mappings.json | Проверенный снимок связей |

Сервер: vip125.hosting.reg.ru, SSH `latitudo-ru`, пользователь u0916578,
корень `/var/www/u0916578/data/www/latitudo.ru`. Не путать с latitudo.pro/easydecking.

Команды из корня проекта (check — чтение; enable/disable меняют рабочую БД и требуют отдельного разрешения):

```sh
php tools/form-crm/migrate.php check 19
php tools/form-crm/migrate.php disable 19
php tools/form-crm/migrate.php enable 19
```

Индивидуальные опции: `form/nd_form<ID>_rest_enabled` и `form/nd_form<ID>_rest_cutover`.
Таблица очереди: `result_id`, `status`, `lead_id`, `attempts`, `last_error`, `updated_at`.
При необходимости сопоставить её с `b_form_result.ID/FORM_ID/SENT_TO_CRM` чтением.

Диагностика по порядку:

1. Есть ли сохранённый результат? Если нет, проверять отправку/валидацию формы, а не CRM.
2. Есть ли запись очереди и включена ли нужная форма? При сбое постановки агент восстанавливает новые пропущенные записи после cutover.
3. Выполняется ли агент, обновляются ли LAST_EXEC/NEXT_EXEC, работает ли cron?
4. При ошибке — прочитать last_error; проверить доступность REST/права вебхука/связи полей.
5. При uncertain/sending — искать лид по точной паре ORIGINATOR_ID и ORIGIN_ID. Не по телефону: один клиент может отправить разные заявки.
6. При подтверждённом ID проверить карточку и историю. Если ошибка только в назначении — проверять правила CRM.
7. Если нет письма — отдельно проверять почтовое событие/шаблон/доставку.

Обработка состояний sending/uncertain старше пяти минут периодически повторяет поиск, но не создаёт лид заново.
Явные ошибки `error` требуют исправления и ручной попытки. Не обнулять lead_id/статус и не удалять запись очереди ради повторной отправки.
Блокировка MySQL GET_LOCK на результат защищает от параллельных попыток. Пара ORIGIN сохраняется в CRM,
но сама CRM не гарантирует уникальность crm.lead.add: поэтому потерянный ответ требует осторожного восстановления.

Замена/отзыв вебхука: согласовать изменение, сохранить защищённую копию файла конфигурации вне www,
создать/выбрать подходящий входящий вебхук в Битрикс24 с нужными правами CRM, обновить серверный секрет,
проверить чтение crm.lead.list и затем согласованную отправку. Точный путь меню вебхуков зависит от интерфейса
(обычно «Разработчикам → Другое → Входящий вебхук»). Этот секрет используют также другие обработчики:
корзина и вложения; проверить их зависимости до отзыва старого ключа. Не отключать двухфакторную защиту ради legacy OTP.

## 9. Остановка, резервные копии, откат

disable выключает очередь для выбранной формы; результат и почта продолжают работать.
Старое подключение остаётся ручным. ID лидов/очередь сохраняются. Общий агент удаляется только после отключения всех форм.
Уже начавшийся запрос может завершиться — проверить sending/uncertain перед откатом.

Повторное enable фиксирует новую границу результатов. Заявки, созданные во время отключения и не попавшие в очередь,
не следует считать автоматически доставленными после включения: проверить этот период отдельно.
Старые записи очереди при включении могут продолжить обработку.

Миграция сохраняет проверенные структуру и затронутые строки вне публичного каталога:
`/var/www/u0916578/data/codex-backups/form<ID>-rest-enable-20261119-*.json`.
Исходники до расширения: `/var/www/u0916578/data/codex-backups/forms-rest-20261119-extend/*.before`.
Перед новой правкой делать новую копию и сравнивать фактический серверный исходник с проверенным.

Откат общих файлов возможен после отключения всех зависимых форм и проверки очереди.
Не заливать старый полный снимок поверх новых результатов, не удалять очередь, не включать автоматически
неработающий старый импорт. JSON-копия — материал для выборочного восстановления, а не команда полного импорта.

Проверки:

```sh
php tools/form-crm/test_delivery.php
php tools/form-crm/test_bitrix.php
```

Второй тест ограничен локальной копией, использует временные таблицы, не создаёт реальные лиды/письма.
Рабочая проверка 19.11.2026: семь тестовых результатов 15201–15207, семь отдельных лидов,
файл претензии, почтовые события, повторная обработка без новых лидов.
Позднее пользователь подтвердил реальную заявку15208 → лид217905 скриншотом.
Сквозная повторная проверка PDF калькулятора в эту проверку не входила.

## 11. Что будет при создании новой формы

**Автоматического подключения новой формы к нашей REST-очереди нет.**
Список разрешённых ID задан в `LatitudoFormCrmDelivery::FORMS` в
`local/php_interface/include/latitudo_form_crm_delivery.php`:

```php
public const FORMS = [1, 19, 21, 22, 23, 26, 27];
```

Кроме присутствия в списке, для формы должна быть включена отдельная опция
`form/nd_form<ID>_rest_enabled=Y`. У новой формы её нет, по умолчанию N.
Копирование существующей формы создаёт новый ID и **не копирует включение REST**.

| Действие | Результат |
|---|---|
| Создать форму, настроить вопросы и вывод на сайте | Форма работает по своим настройкам; наша очередь её не обрабатывает |
| Настроить почтовый шаблон/отправку в компоненте | Отправляются письма; это не включает CRM |
| Скопировать форму с вкладкой CRM и связями | Связи могут скопироваться, но REST для нового ID всё равно выключен |
| Включить в новой форме старый CRM-режим «автоматически» | Возможна попытка старого импорта; это не наш REST и не решение подключения |
| Добавить ID только в FORMS | Недостаточно: нужны проверенные связи и отдельное включение |
| Проверить конфигурацию, затем выполнить enable для новой формы | Новые заявки поступают в очередь после записанной границы включения |

### Если новой форме нужна только почта

1. Сервисы → Веб-формы → Настройка форм → Создать.
2. Задать уникальный SID, название, сайт, вопросы и обязательные поля, статус и права.
3. Заполнить русское название ссылки в меню результатов, чтобы форма отображалась слева.
4. Настроить активный почтовый шаблон `FORM_FILLING_<SID>`, получателей и использование отправки почты компонентом/обработчиком.
5. Вывести нужный ID формы на странице или в модальном окне сайта.
6. Проверить отправку из публичного интерфейса: результат сохраняется, письмо приходит адресату.
7. CRM не подключать. Для отзывов24 и резюме25 именно такой режим согласован пользователем.

Создание самой записи формы не размещает её автоматически на странице сайта и не гарантирует почтовую отправку без шаблона/вызова отправки.

### Если новой форме нужны лиды через вебхук

После обычной настройки формы разработчик выполняет следующие шаги:

1. Получить явное согласование назначения формы, почтовых получателей, передаваемых данных и ответственного.
   При необходимости отдельного ответственного по форме сначала доработать конфигурацию: сейчас начальное значение65 общее.
2. Подготовить проверенную копию затрагиваемых настроек/таблиц перед изменением рабочей базы.
3. Создать/выбрать связь CRM для новой формы и настроить соответствия вопросов полям лида.
   Обязательна непустая связь TITLE. Старый транспорт оставить ручным; вводить старый пароль/OTP ради REST не требуется.
   Если интерфейс старой интеграции не позволяет настроить поля без legacy-авторизации,
   разработчик готовит контролируемую миграцию связей; не ослаблять двухфакторную защиту.
4. Проверить преобразование каждого типа. Телефон/email поддержаны, обычные значения преобразуются в строки;
   новые файловые/множественные/специальные поля требуют отдельной проверки. Особенности CLAIM не включаются автоматически для другой формы.
5. Добавить новый ID в `LatitudoFormCrmDelivery::FORMS`.
6. Дополнить `tools/form-crm/mappings.json`: ID формы, точный SID, CRM_ID и полный проверенный массив FIELD_ID/FIELD_ALT/CRM_FIELD.
   JSON не создаёт связи в базе — они должны уже существовать.
7. Добавить проверки новой формы: связи, постановка в очередь, ORIGIN_ID, создание, ошибка,
   повтор без дубля, статус/ссылка, вложения при наличии. Обновить документацию.
8. После разрешения на прод сверить серверные исходники, сохранить откат и выложить код со снимком связей.
9. Выполнить `php tools/form-crm/migrate.php check <новый ID>`, затем разрешённое
   `php tools/form-crm/migrate.php enable <новый ID>`. Скрипт проверит конфигурацию,
   сохранит копию настроек, отключит старый автотранспорт и включит REST последним действием.
10. Отправить согласованную контрольную заявку именно из нового публичного интерфейса.
    Проверить результат, письмо, единственный лид, все нужные поля/вложения,
    начального и конечного ответственного, статус «Отправлено» и ссылку.

Результаты, созданные до включения REST, автоматически не импортируются.
Если нужно перенести их, отдельно согласовать период/объём и проверить существующие лиды,
особенно если ранее работала почтовая или legacy-интеграция.
